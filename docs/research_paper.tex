\begin{abstract}
This file records the current VFI proof-of-concept implementation for internal review; it is not a submission-ready research paper. The project connects chronological transaction preprocessing, a Flower federated-learning loop over four simulated clients, client-side DP-SGD, a Groth16 proof of a limited output-layer aggregation relation, and smart-contract audit logging. The saved round-10 artifact reports 71.22\% validation F1 on 217 positive and 108,800 negative examples. The separate current final-evaluation artifact reports 67.88\% F1 on 302 positive and 217,732 negative examples. The code does not demonstrate independently operated bank data silos: preprocessing is centralized and the four clients are randomized shards of pooled training rows. The ZK circuit does not prove full-model training, model accuracy, or truthfulness of the reported metrics.
\end{abstract}

\section{Current Pipeline}
The saved preprocessing manifest identifies run ID \texttt{abc4b575614845cdb99a25f3f91aa979}, 1,090,172 input rows, and a chronological whole-timestamp split. The train, validation, and test partitions contain 763,121, 109,017, and 218,034 rows, respectively, with 1,226, 217, and 302 positive labels. The manifest records \texttt{resampling: none}. Causal transaction-history features are constructed after the split; StandardScaler, PCA, and the post-PCA scaler are fitted on the training rows.

The preprocessor shuffles the pooled training feature table and partitions it into four client shards. Thus, these are simulated clients, not source-provided bank partitions. Feature engineering and dimensionality reduction happen centrally before sharding. The classifier is a PyTorch MLP receiving 32 PCA-transformed features; it is not a GNN performing message passing during the federated classification phase.

Flower clients train locally with positive-class loss weighting and an Opacus DP-SGD implementation. The server aggregates with FedAvg and selects the round and decision threshold using validation. The saved final-evaluation record reports maximum client $\epsilon=11.13$ at $\delta=10^{-5}$ and labels its RNG mode \texttt{standard\_prng\_demo\_only}; this does not establish production-secure randomness.

\section{Cryptographic Scope}
The Circom circuit constrains a sample-count-weighted arithmetic relation for 33 quantized output-layer parameters and their Poseidon commitment. The Solidity contract verifies the proof and records the round with associated metadata. The circuit does not prove the full model, local training, correctness of input data, predictive accuracy, or truthfulness of metric values. The stored metrics and model-weight hash are ledger metadata, not all circuit-constrained public statements.

\section{Implementation Limitations and Work Before Submission}
The present evidence supports a software-integration proof of concept, not a deployment across banks. Before making a cross-institution privacy claim, the data pipeline should perform feature construction within independently partitioned clients, and the experiment should use institution-aware rather than randomized pooled shards. A new chronological test period should be reserved after model and threshold selection, since the current physical holdout has been reused during development. Several random seeds and a same-split baseline should be recorded with complete configuration and input-data checksums. The tests should be rerun against the current no-resampling tree; the existing test summary is historical and includes older SMOTE descriptions. Privacy claims should state the full accountant scope and demo-only RNG limitation. Proof claims must remain limited to the relation encoded in the circuit.
